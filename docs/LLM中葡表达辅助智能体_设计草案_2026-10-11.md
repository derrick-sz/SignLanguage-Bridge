# LLM 中葡表达辅助智能体：设计草案

日期：2026-10-11（Asia/Shanghai）。用户已确认第一阶段优先“将已识别词义组织成中葡句子，歧义时请求确认”。本稿补充算法与自动字幕路线，仅交付设计；未接入 LLM、调用付费服务、运行模型或验证生成质量。接口名、预算和验收样本是实施建议，不是当前功能。

## 1. 目标与方案选择

在逐动作字幕闭环之后增加可选表达辅助：保留已确认的识别事件和原始字幕，依据已审核词义组织中文与巴西葡语表达，遇到缺义、关系不明或来源冲突时请求确认。这里的“已确认事件”表示识别系统已提交，不表示动作真值正确；用户确认的表达也不能自动变成训练标签。

| 方案 | 收益 | 代价与边界 | 建议 |
|---|---|---|---|
| 有边界的单智能体：词义检索、上下文读取、表达草案、澄清 | 适合项目的可追溯字幕与接口架构，可分开评价识别和表达错误 | 需要审核词典、句级证据和独立验证；增加异步时延 | 首选 |
| 单次 LLM 文本改写 | 接入最轻，适合先测中葡表达质量 | 缺少明确的词义检索与澄清流程，仍需应用层校验 | 可作为实验对照，不作为无限制字幕替换 |
| 视频直接交给多模态 LLM，端到端输出译文 | 有潜力利用视频和语言信息 | 需要项目对应手语训练/验证、视觉语义对齐与独立资源预算 | 长期研究，不替代近期识别闭环 |

第一阶段只有一个表达辅助智能体，不引入多个智能体互相讨论或开放式工具循环。功能范围是组织表达、询问缺失信息和显示可选解释；自动代替用户回复、目标手语生成、自动训练/切换权重另设阶段。

## 2. 当前材料能支持什么

现有 `CaptionCatalog` 将识别标签与字幕文本分开，支持 `draft/reviewed`；分类路径显示词典，中文 TFNet 路径显示 gloss，尚未转成葡语自然句。共同语义清单当前人工批准 0 项，不能把已存在的葡语文本、中文字幕草案或同名标签当成完成了双语审核。

智能体不会补足关键点协议不一致、动作漏检、词表外拒识或中文识别质量不足。它可能改善文字表达，但是否提高最终交流成功率需要实验；不能将流畅度当作识别正确率提升。

已有 SignLLM 研究利用视觉离散表示、视觉/文本对齐等模块将视频接入 LLM，并在特定 SLT 数据上评价。这说明相关研究路线存在，但不能推导出通用聊天模型已经掌握本项目的 CE-CSL/Libras 或直接满足中巴实时交流。[作者论文](https://arxiv.org/abs/2404.00925)

本期需要新增的数据是审核过的词义、固定表达、句级组合与澄清样例，首先用于检索和评估。不能用未经审核的 LLM 合成译文替代跨手语对应关系、逐词边界或真实标注。训练 backbone 与表达辅助模型分别登记。

## 3. 数据流与字幕呈现

```mermaid
flowchart LR
    A[视频或摄像头] --> B[自动分段与识别 API]
    B --> C[正式动作事件与原始字幕]
    C --> D[本句事件快照]
    D --> E[审核词义及用户确认上下文]
    E --> F[表达辅助智能体]
    F --> G[来源与语义约束检查]
    G --> H[中葡表达草案或澄清选项]
    H --> I[用户确认的表达记录]
```

原始字幕沿已有路径直接显示；辅助草案在独立区域异步更新，不阻塞摄像头、分段和识别。界面保留“原始识别 / 辅助表达 / 待确认信息”三种明确状态，可关闭辅助层并继续使用原始功能。

**动作边界不等于句子边界。**用户每个词后稍作停顿，是分段约定，不能每次停顿都生成一条完整句子。首版使用“整理本句”或明确的句子结束操作选定事件范围；之后再验证更长停顿、结束手势等自动句界。正在输入时可展示明确标注的预览，不能提前代用户提交意图。

例子仅为设计示意：若三个事件的审核义项分别为“我 / 想要 / 水”，并已结束本句，可建议“我想要水。”和“Quero água.”。若只有“水 / 医院”，两者的关系不明，应问“这两个词之间是什么关系？”并提供可编辑选项，不能直接补成“我要去医院买水”。例子不表示当前词表已经有这些模型类别或审核映射。

## 4. 智能体的模块与工具

| 模块建议 | 职责 | 依赖与扩展边界 |
|---|---|---|
| `UtteranceBuilder` | 从 timeline 选择本句事件，产生不可变快照 | 保留 session、参与者、source epoch、顺序与来源时间，不处理视频 |
| `SemanticCatalog` | 维护义项、语言、审核证据、固定表达和允许的组合 | 同名标签不自动合并；缺义保持缺失；现有 CaptionCatalog 可适配，不破坏旧格式 |
| `ConversationContext` | 保存每会话中用户确认的上下文与纠正，限制长度 | 两方/两语言来源隔离；不把未接受草案纳入事实上下文 |
| `CommunicationAgent` | 调用允许的工具，生成表达草案或澄清请求 | 显式状态机与工具次数/时长上限；不获得模型管理或外部发送工具 |
| `LLMProvider` | 统一云端/本地文本模型的生成、取消、能力与错误契约 | 提供者、模型与版本可换；不要把生成任务强制转换成分类结果 |
| `ExpressionValidator` | 校验 schema、引用、审核状态及可检查的语义约束 | 校验通过不等于自由文本含义一定忠实；复杂语义仍需评价和用户确认 |
| `AssistanceStore` | 保存草案、澄清、接受/拒绝和版本 | 与 GestureEvent/CaptionTimeline 的原始记录分开，不覆盖预测 |

首版允许的工具只有：读取指定事件快照、按义项 ID 查询审核词典/固定表达、读取限定的确认上下文。生成澄清请求和表达草案作为结构化输出，由应用层展示。工具参数必须校验会话归属、可访问事件和版本。

开始可固定工具顺序“取快照 → 查词义 → 生成 → 校验”，不要求 LLM 自主选择每一步；遇到多义时再增加有上限的补充检索。应用控制提交与确认，LLM 不能自行提高审核状态、修改识别标签或发送消息。

Function calling 可用于返回工具名和参数，实际调用由应用执行；并不赋予模型直接修改系统的权限。[工具调用官方说明](https://developers.openai.com/api/docs/guides/function-calling)

## 5. 接口契约：保持生成与识别分离

识别 API 继续返回 classification/gloss_sequence 等结果。表达辅助独立声明 `task_type=semantic_assistance`，共享 trace、版本、错误与计时外层，拥有专用请求/结果类型，不复用分类 score 代表语言忠实程度。服务可在同一部署中实现，接口边界应独立。

建议先提供 `POST /v1/assistances` 与按 assistance ID 接受/拒绝/回答澄清的接口；这些均为待实现名称，不改变现有识别 v1/v2 路径。快照与上下文尽量由服务端按授权 ID 装配，不信任客户端声称的 `reviewed` 标记或任意聊天历史。

| 请求字段组 | 必要内容及用途 |
|---|---|
| 身份与范围 | schema version、request ID、session/participant ID、utterance ID、source event IDs；限定本句和两方来源 |
| 版本 | source epoch、timeline revision、context revision、catalog revision、assistance policy version；防止接受过期草案 |
| 任务 | 请求的输出语言 `zh-CN/pt-BR`、表达模式、是否结束本句、期限；场景可选 |
| 证据快照 | 原标签/gloss、审核义项或缺义状态、识别模型版本、原分数类型/质量；识别证据与用户补充分别标注 |
| 用户确认 | 确认的当前义项、语义关系/槽位、用户直接补充；保存是谁何时确认 |

| 响应字段组 | 必要内容及用途 |
|---|---|
| 状态 | `draft / needs_clarification / unavailable / rejected / error`；没有有效草案时文本为空 |
| 身份与版本 | assistance ID、原 request/utterance ID、全部输入 revision；服务端校验并回传 |
| 表达 | 中文与葡语草案、每项内容的事件/上下文依据、仍未确定的部分；输出始终标注辅助生成 |
| 澄清 | 指向具体事件/义项的歧义、简短问题、可编辑备选；不得擅自默认选择 |
| 来源记录 | 词典条目/版本、已批准表达引用、用户补充引用；缺失审核不能伪造引用 |
| 运行记录 | 实际 provider/model/version、policy/prompt version、排队/检索/生成/校验时延及 token 用量（能取得时）；不用 LLM 自评分当校准置信度 |

结构化输出便于稳定解析，但符合 JSON Schema 仍可能包含语义错误；服务必须处理拒绝、截断、非兼容 schema 与不完整返回，并独立校验内容。[结构化输出官方说明](https://developers.openai.com/api/docs/guides/structured-outputs)

## 6. 语义约束与确认流程

1. 只把在当前快照内有效且有依据的内容送入本句生成。低质量/拒识事件不作为成功识别；可提示重做。未审核义项只显示原文及“需核验”，或先让用户明确确认含义，不能直接启用正式双语辅助。
2. 新增主语、意愿、否定、对象关系、数量、时间、地点和姓名等信息必须来自已审核义项或明确的用户补充。上下文引用需列明来源；将上一轮信息带入本句有歧义时请求确认。
3. 对批准的短句模板与已确认槽位，可以确定性渲染双语表达，LLM 负责选择澄清或提出候选。自由组合以草案呈现；规则、同一个 LLM 的二次检查和回译都不能证明原义正确。
4. 允许语法组织与目标语言习惯表达，但不得擅自把已识别事件替换为语境中更常见的词。草案应列出本句义项是否得到表达，遗漏的重要义项应标记并澄清，不能只检查新增内容。若保留 top-k 候选，LLM 重排仅为待用户确认的诊断建议，不改变原预测或原成绩。
5. 接受草案前重新核对会话、timeline/context/catalog revision 与事件有效性。输入已撤销、清空、更正或换源导致草案失效时，拒绝接受并允许重新生成。已确认历史按明确操作保留。
6. 用户确认表达时新增记录；识别原标签和分数保持可查。用户更正可以进入单独的审核队列，不能自动在线更新 backbone、词典或未来会话记忆。

必须分开统计“相对输入证据忠实”与“相对实际手语意图正确”。前者成功但识别输入错了，最终交流仍可能错误。LLM 不应靠补词掩盖原模型问题。

## 7. 调度、资源与失败回退

原始字幕按现有识别链路出现，不等待智能体；表达按句触发，禁止逐帧调用 LLM。每个会话的待生成队列有界，新请求可以取消同一本句的旧草案，终态明确为取消/过期，不能把旧文本回填。

开始采用单 provider 的文本 API 测试质量，不绑定具体型号或 agent 框架。`LLMProvider` 声明结构化输出、工具调用、取消、上下文/token 上限与部署位置；OpenAI 兼容路径不代表所有供应商行为一致，必须做能力探测与契约测试。保留无 LLM 的审核词典/模板回退。

之后用同一冻结语料比较云端与本地多语言指令模型，覆盖中文、巴西葡语、否定、数量、角色和歧义，依据忠实度、成本、时延与资源选型。没有项目实测前不承诺某个参数规模或量化方式满足效果。

识别的 ONNX/CUDA 运行时与 LLM 的生成运行时分别适配；不要求所有 LLM 转成当前分类 ONNX 模型。若本地共用 GPU，优先保障摄像头特征/识别，设置生成并发与 token 上限；模型载入、显存竞争、长上下文和两会话压力须实测后再开启常驻。

默认只传完成辅助任务所需的结构化文本，不传摄像头帧或完整视频。云端数据发送由明确的产品设置控制，日志隐藏密钥并限制对话保存；本轮文档工作不发送任何业务语料。

超时、断网、额度不足、模型不可用、校验失败时显示明确状态，原始字幕继续；只有词义/槽位具备足够依据才使用确定性模板，否则保持原文。服务恢复后不能自动替用户确认先前草案。

单独测量“本句结束 → 辅助草案可见”和“澄清确认 → 最终辅助表达”。可将短句草案 P95≤3 秒作为首轮实验预算候选，验证后冻结；它不是当前成绩，也不能代替原路线动作结束到原始字幕 P95≤2 秒的目标。分别报告两路、冷启动、失败率、并发和 token 成本。

## 8. 数据准备与评价

从双方审核词表和真实录制中构建小型句级测试集，保存手语/事件证据、审核义项、允许译文、不能推断的槽位、应澄清项以及用户补充。固定短句的单分类标签作为一个完整语义单元，不能按显示文本的空格重新推造逐词证据。

两种输入条件分别测：人工核验事件评估表达层；模型真实事件评估整个交流链路。词典查表/模板是基线，单次 LLM 与检索约束智能体是对照。没有动作真值的演示只能证明运行链路。

| 指标 | 口径与用途 |
|---|---|
| 语义忠实 | 双语审核者判断生成是否与输入支持的含义一致；列出否定、数量、角色、时间/地点改变 |
| 无依据内容 | 草案中至少一项无法归因于事件或已确认上下文的比例；不能把未提交草案排除后报“全零” |
| 歧义与缺义 | 需澄清样本的澄清召回及不必要澄清率；衡量是否既谨慎又可用 |
| 表达覆盖 | 能产生有用草案的样本比例；拒绝、超时等进入分母，防止全拒绝取得高忠实 |
| 两语言质量 | 中文和巴西葡语分别审核可读性与原义；不能只依赖 BLEU、模型自评或回译 |
| 用户体验 | 确认/修改次数、用户纠正耗时和任务完成率；需真实用户验证 |
| 运行可靠性 | 过期草案丢弃、撤销清空、会话隔离、取消、断网回退、资源上限与实际时延 |

首轮可准备至少 100 个审核样例，覆盖正常、缺义、多义、漏词/错词、否定、数量/角色、重复、上下文冲突与会话隔离。样例规模是试点建议，按能取得的审核人员和覆盖范围收缩功能声明；不能凭少数样例宣称通用翻译。

工程门槛：不覆盖原始识别、不用 LLM 修改审核状态、过期响应不能显示/接受、供应商错误不阻塞字幕、无任何跨会话信息流。语义门槛在首轮标注试验后、留出评价前冻结；不能事后只报告流畅样例。

## 9. 接入顺序与后续扩展

| 阶段 | 与原路线关系 | 交付与退出条件 |
|---|---|---|
| L0 契约与评估集 | M0/M1 完成稳定事件身份后，可设计接口与夹具 | 快照、句界、审核状态、版本与回退契约明确；不调用 LLM 也可回放 |
| L1 审核词义/模板 | 复用 M3 词义审核，可与 M1/M2 并行准备 | 有可声明范围的已审核表达集；0 项审核时只测试契约/人工样例，不能声称上线双语辅助 |
| L2 表达辅助最小实现 | 不阻塞 M2 摄像头与 M3 模型训练 | 一个 provider、独立草案区、检索与澄清、用户接受/拒绝、真实接口与冻结语料评价 |
| L3 本地部署与双路可靠性 | 与 M4 合并性能验证 | 实际两路时延、资源隔离、断网回退和会话隔离满足冻结要求 |
| L4 更开放的交流辅助 | M5 的可选分支 | 可选回复、场景词义和句法辅助需独立评价；场景仍不是核心必填 |
| L5 视觉/LLM 联合研究 | M5 研究线 | 有本项目手语/文本监督和视觉对齐后再比较，不将现有文本智能体称为端到端手语模型 |

后续可增加“解释这条表达”“给出可选回复”“生成双语交流摘要”，均引用原始事件与用户确认记录，并保留用户选择。模型错误分析助手可单独读取脱敏报告提出补采建议，但不自动重训或更换线上模型。

本稿保留 LLMProvider 和工具边界，具体框架与型号在真实语料/资源测试后决定。新增 LLM 设计不自动扩大已启动的“自动字幕与可扩展模型 API 开发”会话任务；该会话先交付识别、分段和 timeline，后续实现按本稿另定范围。
