## 3. 关键发现：延迟改变了组合策略的优先级

**如果延迟是硬约束（实时/交互场景）**：
- 唯一可行 = **纯 A2**（278 ms）或 **纯 A**（2.7 s）
- 任何涉及 SLRT 或 LLM 的组合都超过 5 秒——不可部署
- 确定性槽位修补（并行模型 5.5 s）在"准实时"场景可能勉强

**如果延迟可容忍（批处理/离线翻译）**：
- 确定性槽位修补（5.5 s）可行
- 槽位修补 + LLM 润色（8.5 s）也可行
- 但需要证明质量提升值得这个延迟

**用户提出的两步管线**：
```
Uni-Sign 翻译（2.7 s）+ SLRT 识别（5.5 s） [并行]
    → 确定性槽位修补（~0 ms）
    → LLM 句法润色（2-4 s）[仅当修补触发]
    → 最终译文
```
总延迟 ≈ **并行模型 5.5 s + 条件 LLM 3 s ≈ 8.5 s（最坏）/ 5.5 s（无触发）**

这比"每句都调 LLM"好（选择性调用），但仍然 >5 秒。

## 5. 用户两个问题的直接回答

### Q1：句法流畅不可以通过 LLM 进行完善么？

**可以，但要分两步做而不是一步**：
1. **第一步（确定性，不调 LLM）**：槽位修补——用 SLRT 高置信 gloss 词替换 A 句子中的错误内容词。这步保留 A 的句法骨架，只改事实。
2. **第二步（条件性，调 LLM）**：如果修补后的句子"不够自然"（比如替换后的词不合句法），才调 LLM 做纯润色。**但 LLM 只管通顺，不看事实**——给它修补后的句子，让它"把这句话改得更自然，但不改变任何事实"。

**为什么之前 C 组失败但两步管线可能成功**：C 组给 LLM 的是"通顺但事实错误"的原句，LLM 无法判断该改什么。两步管线给 LLM 的是"事实已修正但可能不够通顺"的句子，LLM 只需要做它擅长的事——润色。

**但延迟是硬伤**：加 LLM 润色至少 +2 秒，总延迟 8.5+ 秒。只适合批处理。

### Q2：推理延迟被忽略了？

**是的，这是 G2 决策的盲区**。G2 验收三问的第三问是"增加的计算成本是否值得"，但我们只报了 token 数和单次 P50/P95，**没有把总管线延迟纳入"是否值得"的判断**。

修正后的结论：
- **实时场景**（用户对着摄像头打手语，期望 <2 秒出字幕）：**只有 A2/A 单模型可行**，任何组合都太慢
- **批处理场景**（上传视频离线翻译）：**确定性槽位修补可行**（5.5 s），但需要 task-26 证明质量有提升
- **LLM 润色只适合离线精品翻译**（8.5+ s），且质量增益尚未证明
