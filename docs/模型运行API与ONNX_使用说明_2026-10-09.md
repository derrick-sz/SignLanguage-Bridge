# 模型运行 API 与 ONNX 使用说明

当前版本 0.2.0，HTTP 契约 v1。桌面和 API 使用同一 `ModelManager` 实现，但分别启动时各自拥有模型实例；桌面当前直接调用本地核心，不依赖 HTTP 服务。API 支持完整动作片段分类。摄像头客户端应完成一个动作录制后上传视频，连续流接口待后续模型具备相应能力再实现。

## CPU 服务启动

在仓库根目录使用现有 Python 3.12 环境：

```powershell
.venv-libras/Scripts/python.exe -m pip install -r requirements-api.txt -r requirements-onnx.txt
.venv-libras/Scripts/python.exe -m pip install -e .
.venv-libras/Scripts/python.exe -m slbridge.api_cli --catalog configs/runtime-models.example.json --model libras-onnx --device cpu
```

浏览器打开 http://127.0.0.1:8765/docs 可查看完整入参、出参并上传文件调用。安装后的命令为 `slbridge-api`。当前工作区已经存在示例配置对应的 RF 与 ONNX 模型包；新克隆的仓库不包含模型、视频或验收产物，应先训练/导出模型并修改目录配置。RGB 视频识别还需要 `requirements-libras.txt`，API/ONNX 依赖本身不包含 MediaPipe。

配置文件格式：

```json
{"schema_version":1,"models":{"libras-rf":"../path/to/rf-bundle","libras-onnx":"../path/to/onnx-bundle"}}
```

路径相对配置文件解析。客户端选择别名，不传服务器模型路径；模型包必须来自可信本地训练/导出，接口不接受上传权重。默认单 worker，避免每个 worker 重复加载模型与占用显存。

## 统一输入和输出

| 接口 | 方法 | 作用 |
|---|---|---|
| `/v1/health` | GET | 当前状态、有效版本、可回退版本及上次切换错误 |
| `/v1/models` | GET | 服务端已配置的模型别名与当前模型说明 |
| `/v1/models/switch` | POST JSON | 选择别名及运行设备，校验、预热后提交 |
| `/v1/models/rollback` | POST | 恢复保留的上个模型，generation 仍递增 |
| `/v1/recognitions` | POST multipart | 上传单个动作片段并识别 |

识别字段：`file` 必填；`request_id` 可选，省略由服务生成 UUID；`representation_id`、`sign_language` 可选，但声明后必须与模型一致。请求 ID 是 1–128 字符的字母、数字及 `_.:-` 标识。支持 MP4/AVI/MOV/MKV 视频及与模型匹配的 NPY/NPZ；RGB 缓存使用带时间戳的 NPZ，不能用旧 NPY 替代。

```powershell
curl.exe -X POST http://127.0.0.1:8765/v1/recognitions -F "file=@demo.mp4" -F "request_id=demo-001" -F "sign_language=libras" -F "representation_id=mediapipe225_rgb_v1"
```

响应结构如下，具体分类分数和耗时由本次调用产生：

```json
{
  "schema_version": 1,
  "request_id": "demo-001",
  "model_generation": 2,
  "result": {
    "status": "recognized",
    "sample_id": "demo-001",
    "model_id": "libras-rf-onnx-20261009",
    "sign_language": "libras",
    "task_type": "classification",
    "score_type": "uncalibrated_class_probability",
    "prediction": {
      "label_id": "item:105",
      "score": 0.89,
      "scores": {"item:105": 0.89},
      "display_text": {"pt-BR": "Árvore"}
    },
    "quality": {},
    "reason": null,
    "time_range": null
  },
  "runtime": {"backend":"onnx_classifier_v1","requested_device":"cpu","device":"cpu","providers":["CPUExecutionProvider"],"fallback_reason":null},
  "timing_ms": {"preprocess_ms": 1400.0,"inference_ms": 0.3,"total_ms": 1400.4}
}
```

示例省略完整类别分数和运行说明字段。`prediction` 保存完整标签分数；`rejected` 时为 null，`reason` 解释质量或阈值拒识。这两类均返回 HTTP 200。模型分数不是正确率。模型结果只返回包内释义；桌面中文词典覆盖仍由字幕层完成，不在模型 API 中伪装为跨语言翻译。

`preprocess_ms` 包含文件读取、解码、关键点提取及模型前处理；`inference_ms` 是适配器的数值预测；`total_ms` 是管理器内调用时间，不包含上传、HTTP 网络往返和响应序列化。缓存 NPZ 时延不能代表摄像头端到端时延。

前端保存当前 `model_generation`，切换成功后清空旧结果；收到延迟响应时，用请求 ID 与 generation 检查是否仍属于当前展示。字幕词汇也应依据有效模型说明更新。

错误统一为 `{"schema_version":1,"request_id":"...","error":{"code":"...","message":"..."}}`。409 表示当前任务/切换占用容量；503 表示模型不可用；422 表示输入或模型配置不兼容；413 表示请求/文件超限。默认上传上限 128 MiB，可用 `--max-upload-mb` 调整；NumPy 容器还会在分配数组前检查形状、展开大小及压缩包内容，损坏文件作为输入错误返回。

## 切换与回退

```powershell
curl.exe -X POST http://127.0.0.1:8765/v1/models/switch -H "Content-Type: application/json" --data-raw '{"model_id":"libras-onnx","device":"cpu"}'
curl.exe -X POST http://127.0.0.1:8765/v1/models/rollback
```

运行管理器一次处理一个识别请求。正在推理时切换返回 409；候选准备期间新识别也返回 409。候选校验和预热成功才切换，失败保留当前模型和 generation。保留一个旧实例供回退；准备下一个候选前会释放更旧的回退实例，将驻留数量限制为两个。CUDA arena 上限是每 Session 的内存选项，不是整个进程显存的硬上限。

桌面“设置”中可选择兼容 RGB 模型及恢复上个模型。录制期间禁用切换，取消/来源变更会使尚未提交的候选失效。模型包绑定处理流水线与标签，显示词典按当前手语语种匹配。

## CUDA 部署与实际验证

GPU 环境安装 `requirements-onnx-gpu.txt`，CPU 和 GPU 两种 ORT 包只能选择一种。使用独立虚拟环境可避免覆盖现有环境：

```powershell
python -m venv .venv-gpu
.venv-gpu/Scripts/python.exe -m pip install -r requirements-libras.txt -r requirements-api.txt -r requirements-onnx-gpu.txt
.venv-gpu/Scripts/python.exe -m pip install -e .
.venv-gpu/Scripts/python.exe -m slbridge.api_cli --catalog configs/runtime-models.example.json --model libras-onnx --device cuda --cuda-dll-dir "D:/NVlDlA GPU ComputingToolkit/bin" --cuda-dll-dir "D:/NVlDlA GPU ComputingToolkit/bin/12.9"
```

DLL 目录是本机已验证路径，其他设备应按实际 CUDA/cuDNN 安装修改。路径仅由服务启动配置，不接受客户端传入；加载仅影响本进程，不修改系统 PATH。`auto` 尝试 CUDA，可回退 CPU并返回原因；`cuda` 要求实际 Session 启用 CUDA，初始化失败会拒绝候选；`cpu` 固定 CPU。桌面启动命令也支持这些运行选项。

运行可复现的 GPU 检查：

```powershell
.venv-gpu/Scripts/python.exe -m experiments.validate_onnx_gpu --output artifacts/gpu-check --cuda-dll-dir "D:/NVlDlA GPU ComputingToolkit/bin" --cuda-dll-dir "D:/NVlDlA GPU ComputingToolkit/bin/12.9"
```

此检查使用未训练 MatMul 图，验证生产适配器、CUDA 节点 profile 和 CPU/GPU 数值一致性，不评估识别准确率。CUDA provider 出现在 Session 中不代表所有节点在 GPU；现有 RF 的 TreeEnsemble 算子实际仍在 CPU。后续 TCN/GCN 的支持算子再使用 GPU，并针对实际图检查节点分配。

CUDA/cuDNN 需与固定 ORT 1.23.2 兼容，不能只依据 `nvidia-smi` 显示的驱动 CUDA 版本。本机另有原生库加载顺序问题：管理器启动先初始化可选 ORT，导出工具先初始化 ONNX/ORT 再导入转换器；RF 已加载的 Python 调用会使用隔离导出进程。依据见[ORT 官方 CUDA 文档](https://onnxruntime.ai/docs/execution-providers/CUDA-ExecutionProvider.html)。

## 导出与性能验收

导出必须提供冻结 validation/test 数据中的真实留出输入，文件 hash 与原模型保存的索引匹配。可重复传 `--verification-input`，也可提供 JSON：`{"schema_version":1,"samples":[{"path":"/absolute/heldout.npz"}]}`。

```powershell
.venv-libras/Scripts/python.exe -m slbridge.export_onnx --model artifacts/experiments/libras-rf-pilot-20261009/models/libras-rf-pilot-20261009 --output artifacts/models/my-onnx-v1 --run-id my-onnx-v1 --verification-manifest artifacts/my-holdout-inputs.json
.venv-libras/Scripts/python.exe -m experiments.validate_model_runtime --native-model artifacts/experiments/libras-rf-pilot-20261009/models/libras-rf-pilot-20261009 --onnx-model artifacts/runtime-acceptance-20261009/models/libras-rf-onnx-20261009 --output artifacts/runtime-check
```

权重、标签、处理契约和文件 hash 一起发布到新目录；目标目录存在时拒绝覆盖。导出前验证概率、标签和阈值决策一致性；原评价记录复制并明确来源，不将导出视为新训练或精度提升。完整 HTTP 视频复测可使用 `experiments.validate_model_api --catalog ... --input ... --output ...`。

后续复杂 backbone 的执行顺序是原框架训练/冻结评估 → ONNX 导出 → 同输入精度对比 → CPU/CUDA 设备与算子检查 → P50/P95 预处理/推理/端到端测量。FP16、量化、I/O Binding、TensorRT 和动态批处理均留到测量证明有收益后引入；当前没有假设通用时延保证。
