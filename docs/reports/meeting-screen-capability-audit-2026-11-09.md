# 在线会议屏幕选区：当前能力与产品方向

日期：2026-11-09，Asia/Taipei。本文为当前源码与本机服务的只读核查和方案建议，尚未实现或验收屏幕采集功能。

用户明确的主场景：在电脑屏幕上框选手语者所在的视频区域，不绑定某个会议软件；持续识别画面并输出文字字幕。文字转手语保留为其他场景下的辅助功能。

**比赛Demo范围修订：** 用户随后明确只需比赛演示，优先保留Web端。本轮推荐改为“浏览器共享屏幕/窗口 → 网页预览中框选 → 分段识别 → 页面字幕追加”，复用现有本机识别服务；桌面小助手作为可选后续，不属于当前Demo范围。当前仅更新方案，尚未实现屏幕采集。

## 当前已具备什么

| 层次 | 当前事实 | 对会议场景的含义 |
|---|---|---|
| `/communicate/`采集 | `CameraCapture.open()`调用`getUserMedia`预览本机摄像头；单次录制最长12秒，`onstop`产生完整文件并停止设备轨道 | 已有摄像头接入代码，仍不是持续采集识别；本轮没有启用设备实测 |
| 产品识别提交 | `RecognitionController.recognize()`发送完整文件；网关协商和调用均明确`mode=clip` | 录完再识别，不会在录制过程中输出字幕 |
| 当前在线中文模型 | 8765真实`/v3/models`返回`cecsl-tfnet-onnx-20261009`、`task_type=gloss_sequence`、`modes=[clip]` | 返回手语词序列，不能直接承诺自然中文整句翻译或原生增量识别 |
| 当前在线Libras模型 | `libras-rf-pilot-20261009`、`task_type=classification`、`modes=[clip]` | 12词试点，不承担开放会议句子识别 |
| 桌面研究基础 | 已有`VideoSource`/`CameraSource`、`FramePacket`、`AutoSegmenter`、`CaptionLedger`及独立SLRT面板 | 有可复用的采集、分段、事件基础，尚未连接屏幕选区与当前产品页；模块存在不等于会议验收通过 |
| 屏幕框选和字幕浮窗 | 当前源码未见`getDisplayMedia`、`tabCapture`、`QScreen.grabWindow`或桌面框选实现 | 需要补开发；不能把摄像头预览称为已支持任意会议视频流 |

本轮没有采集屏幕、访问摄像头/麦克风、运行新模型评测或改变8765/8879服务。此前真实上传验证与动作修订保留各自范围，不能推广成在线会议识别正确率或延迟证据。

## 推荐交互

**开始字幕 → 浏览器选择共享屏幕/窗口 → 在网页预览中框选手语者 → 持续采集与分段识别 → 页面字幕追加结果。**

主控制只有开始/暂停、重新框选、字幕显示和会话记录。框中需包含手语者脸部、上半身和双手；文字转手语放在辅助工具中，不占会议字幕主界面。

首版固定桌面Chrome与现有本机服务，预览中选择单一矩形区域。前端按实际视频尺寸与预览缩放映射选区，使用Canvas裁剪送入识别；这不要求开发桌面exe或对接会议SDK。直接共享屏幕时，输入是当前屏幕可见内容，窗口移动后可重新框选。多显示器、跨浏览器和常驻置顶字幕窗不属于首版必做范围。

字幕先显示本机识别结果和时间，可编辑、导出。原始词序列与后续表达辅助草稿分开；没有新增句子翻译器时，不将词序列标成已经翻译好的自然中文。让其他参会者看到字幕可另行共享字幕窗；写入各软件自带字幕通道另有平台对接范围。

## 两条可行接入路线

| 路线 | 优点 | 代价与范围 |
|---|---|---|
| **比赛Demo推荐：现有网页＋屏幕共享＋预览框选** | 可复用当前网页；`getDisplayMedia`可获取用户选择的屏幕/窗口视频流，Canvas可裁剪视频选区 | 先通过浏览器选择共享来源，再在预览中框选；字幕先显示在网页中 |
| 可选后续：Windows桌面小助手＋现有本机服务 | 可直接在桌面拖框，独立字幕窗适合与会议软件并用；仓库已有PySide6桌面基础 | 新增屏幕源、选区层和字幕窗，超出本次比赛Demo必做范围 |

Qt官方[`QScreen.grabWindow`](https://doc.qt.io/qtforpython-6/PySide6/QtGui/QScreen.html#PySide6.QtGui.QScreen.grabWindow)提供屏幕区域像素采集基础，也说明高DPI像素尺寸和遮挡的边界；这是可行API依据，未证明本机持续采样速度。[浏览器屏幕采集](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getDisplayMedia)返回用户选择来源的`MediaStream`，需用户操作启动并逐次选择共享来源。

Web选区可使用[`CanvasRenderingContext2D.drawImage`](https://developer.mozilla.org/en-US/docs/Web/API/CanvasRenderingContext2D/drawImage)：其输入支持视频元素，并可指定源矩形裁剪。纯Web在这里指前端使用浏览器，模型仍运行于现有本机后端。比赛可以用另一窗口播放真实手语视频模拟会议画面，实际采集选区并调用模型，报告中区分屏幕回放演示与真实会议验收。

## 连续识别需要补的工作

1. 为选区帧保留单调时间戳、源身份及尺寸/DPI信息。重新框选、暂停和结束应隔离旧结果，释放所属采集资源，保留已提交字幕。
2. 接入活动/可见性检查与自动分段。静态手势可能有意义，不能仅因低运动就判动作结束。先实现词或短句完成后追加字幕，过程中显示正在识别状态。
3. 初版可复用完整片段服务，每段编码成可独立解码的完整视频并验证输入协议；不能把任意编码字节块当作完整片段上传。采集和推理分工运行，队列有界，积压或超时应明确提示。
4. 复用字幕事件身份、顺序和来源世代保护；同一片段重试不重复提交，重复说同一个词仍能形成不同字幕事件。可修订草稿与提交字幕分开。
5. 识别模型适配是独立验收项。会议压缩、小画面、背景、陌生签者以及连续表达均需实测；已有clip模型和研究流式面板不保证可直接交付会议级实时翻译。

## 验证应如何分开

- 先用另一软件播放已知视频，真正框选该窗口中的视频区域，验证持续采集、识别请求与字幕显示、暂停/重选、DPI和积压。这是屏幕回放工程验收，不能称真实会议语义验收。
- 再用真实会议输入核对文字质量，并记录画面动作结束到字幕可见的延迟、字幕修订、重复提交与漏段。没有配对标注时仅报告链路和时延，不报告识别准确率。
- 采集FPS、模型耗时、首个草稿和稳定字幕延迟分别记录。当前没有本场景的P95或准确率结果，不在方案中保证具体数值。
