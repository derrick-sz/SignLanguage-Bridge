# 实时视频流延迟优化与应用收尾

日期：2026-11-11，Asia/Taipei。场景：中巴手语交流项目，沿用 SLRT 增量词、Uni-Sign 句末中文、可选 LLM 辅助。用户要求兼顾演示与效果，并优先解决实时视频积压。本轮没有更换权重、帧率、图像尺寸、投票或自动分句阈值。

## 结论和原因边界

发现并去掉每帧重复的 canonical 图像转换/缩放，以及网页每个 ACK 都重建字幕/历史的开销。原始输入、预处理像素和133点坐标契约保持一致。8个成对输入的词/句/重置事件完全一致，优化后原生串行阶段的每帧耗时中位数由25.21ms降至21.06ms。

此前服务运行22.8小时后的持续吞吐退化仍未确定根因。当时黑帧姿态约35.5ms/帧，已超过30FPS的33.3ms预算，人物输入和旧已通过样例均过载；相同代码/配置/权重重建服务后恢复。当前空闲识别进程做受控 Windows 工作集回收，RSS由916.7MiB降至0.203MiB，随后3个回放全部完成，人物姿态14.97ms/帧；**没有复现持续35ms退化，因此不能归因于简单驻留内存变化**。工作集API含义参考微软 [EmptyWorkingSet](https://learn.microsoft.com/en-us/windows/win32/api/psapi/nf-psapi-emptyworkingset) 与 [Working Set](https://learn.microsoft.com/en-us/windows/win32/memory/working-set)。未改变全局GPU/电源/内存策略，未设置周期重启。

## 持续流

`continuous-10min/summary.json`：同一WebSocket按30FPS连续重复两个已冻结视频，带1.2秒尾帧、显式句界、0.5秒黑帧分隔。这是合成连续负载，不是真人连续对话或语义正确性验收。

- 实际603.92秒，18112帧发送/确认/处理一致，输入丢帧0，过载0。
- 128句提交，翻译拒绝0，句末任务峰值1，最大等待546ms。
- 排队P50 0.14ms、P95 171.96ms，队列峰值13帧，未扩大16帧上限。
- 姿态15.20ms/帧，图像复用0.0045ms/有效帧，SLRT窗口26.39ms/窗。
- 该阶段完成后另将初始化时的pipeline元数据读取移到native租约之前，避免反向取锁。推理、worker、输入和队列代码相同；最终部署另做冷启动/浏览器检查，不将该10分钟冒充最后这3行初始化改动后的再次长测。

## 工程和应用行为

- RTMPose返回本次姿态使用的320px图像，SLRT直接复用；逐窗口像素一致回归通过，旧前端接口仍兼容。
- 每次会话在同一native worker内对已有detector、pose、S3D做有界预热；空检测也强制暖pose图。清空检测/帧缓存，模拟帧不进入识别流，不额外复制模型。
- ACK更新轻量指标，不触发整个字幕/历史snapshot；300次ACK不调用主渲染的回归通过。词/句事件照常立即显示。
- 活动会话和上一会话保留有界数字性能摘要（最近512处理帧分位数及累计原生计时），取消/过载同样保留，不含视频/识别文本/凭据。重复快照不会重复累计。
- 新增“完成本句并暂停”：先排完当前编码，再明确finish并等已有帧与句末译文交付。文件EOF复用同一路径。中止/换源/后台仍立即作废未完成句，迟到结果不能回写。
- 不根据练习目标句删除输出或回填模型。“完成本句”改善显式收尾；自动分句误追加问题仍需单独验收。
